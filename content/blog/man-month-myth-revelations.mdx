到今天，大约是我开始 Vibe Coding 的第一个整年。

一切的起点，是厦大小学期的一门 Python 程序设计实践课，以及一份不知道从谁那里听来的 GitHub 学生认证包。

我就这样打开了 Visual Studio Code，点开内置的 Copilot。那时使用的模型还是 GPT-4o。

这是一切的开始。

今年的小学期也刚刚结束。仅仅一年，AI，尤其是 Coding Agent，已经发生了翻天覆地的变化。

但回头看，我越来越觉得，真正改变的不只是模型的能力，也不只是软件开发的速度。变化更深的地方在于：软件工程中最昂贵的部分，正在从“如何写出代码”，转移到“如何定义目标、维持一致性、同步上下文、验证结果，以及做出最后的决定”。

AI 没有终结《人月神话》。

它只是让“人月神话”换了一种形态。

## 一、草履虫爬出了火山口

梦开始的地方，是一个叫作 **Tripy Web** 的项目。

我一直是一个对项目名称很纠结的人。不能说苛刻，可能只是单纯的选择困难。但每一个名字，我又总希望它背后有一点意义。

Tripy 里的“tri”是三，因为当时的程序设计小组有三个人；“py”是 Python，因为我们做的正好是 Python 课程设计。连起来，就是 Tripy。

现在看起来有一点幼稚，但那时我确实很满意。

2025 年六月底，我对软件开发几乎一无所知。

当时还没有人天天对你说：

“AI 是万能的，有什么直接交给它就好了。”

那时没有那么普及的 Prompt Engineering，没有 Context Engineering，小龙虾还在孕育，Claude Code 正风行一时，但我舍不得充值。Codex 还只有 CLI，甚至仍处于 EA 阶段，也还没有后来那次 Rust 重构。

当然，这些都是后来才知道的。

当时的我只是在 ChatGPT 网页版里，用着免费账户每天十来条消息的额度，准备问 GPT-4o：

“我要做一个 Python 程序设计课设……”

字打到这里，我突然停住了。

因为我发现，我根本不知道下一步该问什么。

我要做一个项目。

可是项目是什么？

为什么一个项目还要分前端和后端？

数据库又是什么？

我什么都不知道。

最后，我还是把那句几乎没有任何信息量的话发了出去：

“我要做一个 Python 程序设计项目。”

在那个还没有“提示词工程”概念的年代——虽然也就一年前，一年前都已经能叫年代了🤣——GPT-4o 给我推荐了几个项目方向。

我和我的 partner 最后选择了个人博客。

摸索了一会儿，我发现 Copilot 里居然也有 GPT-4o，而且它甚至可以帮我执行一些命令。

那一刻的体验真的很奇妙。

我去完成了 GitHub 学生认证，拿到了不少额度，随后向 Copilot 表达了构建博客系统的需求。

我已经记不清当时具体说了什么，大概无非是：

“帮我做一个博客系统。”

Copilot 给我的，是一个 HTML 页面。

一个非常原始的 HTML 页面。

上面只有登录框、账号、密码、注册和登录按钮。没有什么设计，没有真正的业务逻辑，甚至连“系统”都很难称得上。

但对当时的我来说，那一刻真的像是：

> 草履虫第一次爬出了火山口。

我没有动手写代码，一个网页就这样呈现在了我的面前。

紧接着，我也很快被泼了一盆冷水。

当时的 GPT-4o 没有什么真正意义上的 reasoning，没有稳定的长链路规划能力，更没有针对 Agent 工作流完成大量轨迹训练。

它可以给我一个页面，却无法真正替我构建一个系统。

那个 Web 项目最终也就是几个简单的表单、登录页面和零散功能。很快，我又开始刷到什么就想用什么。

想把后端换成 FastAPI。

过几天又觉得 Django 更专业。

前端想从原生 HTML 换成 Vue。

后来又接触到 Vite。

现在看来，这是一种非常典型的“第二系统效应”：第一个系统还没有真正完成，我就已经急着把所有新看到的技术都塞进第二版里。

过去，重构的成本足够高，人往往会因为麻烦而克制自己。

但 Agent 降低了“开始重构”的门槛。

你只需要说：

“把这个项目完整迁移到 Vue。”

“把 FastAPI 换成 Django。”

“把前后端全部重构。”

每一个技术冲动，看起来都只需要一句话。

可问题是，Agent 让重构更容易开始，却没有让重构更容易结束。

框架迁移之后，数据模型会不会变化？

接口语义会不会变化？

构建方式、部署方式、登录状态和原有逻辑能不能保留？

这些复杂性并没有消失。

当时的 Copilot 甚至无法稳定处理 Vue 和 Vite 编译时输出的日志。这大概也成了我早期使用 Coding Agent 时，心里留下的一道伤。

Git 操作不敢交给它。

前后端开发服务器的启动不敢交给它。

遇到报错，只能复制粘贴。

稍微涉及环境，我就开始失去控制。

思考的时代还没有到来。

而我在没有掌握模型的时候，就已经想让模型独立做事。

现在回看，那确实是一座空中楼阁。

## 二、思考的时代，与第一个外包项目

八月，GPT-5 到来。

随后是 o1-mini、o3-mini，以及 DeepSeek V3。

思考的时代终于开始了。

痛定思痛之后，我在 2025 年九月给美区账户充值了 20 美元，正式订阅了 ChatGPT。

动机很明确：Codex GA。

当时 Codex CLI 的版本号大约是 0.36。

在 Claude Code 的风头之下，Codex 并没有引起太大的波澜。但它带领我完成了第一个真正意义上的外包项目后端：

**Suanxian。**

[查看 SUANXIAN 项目介绍](/works/suanxian)

那时，Codex Cloud 还处在促销阶段，可以近乎无限使用。

早期 Cloud 的设计非常原始，也非常激进。

它会在宿主机上克隆你的 GitHub 仓库，配置环境，执行任务，最后给出一个 Pull Request。

从想象上看，这一切都非常合理。

代码在远端运行，Agent 自己完成修改，你只需要审核 PR。

但真正使用后，我很快发现：如果只是这样，那么它和我在网页版 ChatGPT 里对话，最后复制代码回项目，究竟有什么本质区别？

当然，多了一个 PR 按钮。

但也仅仅只是多了一个 PR 按钮。

那时的模型速度很慢，宿主机又需要完成克隆、配置环境、安装依赖、网络传输等一系列流程，最终的反馈非常差。

最致命的问题是：

> 它无法做到所见即所得。

你不知道它当前理解了什么。

不知道环境到底配成了什么样。

不知道任务跑到哪一步。

不知道它是卡住了，还是正在犯错。

甚至它最终提交的 PR，本身也可能带着 P0 Bug 和明显的逻辑谬误。

但它无限使用啊。

于是我一口气扔出去十几个并行任务，最后把十几个 PR 一锅乱炖，合进了外包项目的代码库。

现在看来，这几乎是 Agent 时代最标准的一次“人月神话”复现。

传统的人月神话认为：

> 给一个已经延期的软件项目增加更多程序员，往往只会让它更加延期。

因为新增的人需要理解项目，需要沟通，需要协调接口。人数增加之后，沟通成本并不会线性增长，而会迅速膨胀。

Agent 看起来绕开了这个问题。

它不需要入职，不需要开会，不会疲惫，也不会和你争论。你可以同时复制十个、二十个，让它们并行工作。

可是，Agent 只是把人与人之间的沟通成本，变成了另一种成本：

- 每个任务拿到的上下文是否一致？
- 不同 Agent 做出的架构决定是否冲突？
- 多个 PR 之间是否存在隐含依赖？
- 谁来判断哪一种实现才是正确的？
- 谁来负责最终集成？
- 谁来确认这些代码共同构成的，仍然是同一个系统？

Agent 可以并行生成代码。

但它不能天然并行生成一个概念完整的软件系统。

这大概是我烧掉 Token 后，最早真正理解的东西。

最好的经验，从来不只是“让模型替你完成任务”。

而是你在烧掉 Token 的同时，开始理解当前模型的行为，理解 harness 的行为，也理解它们的边界。

当时如此，现在依然如此。

## 三、CLI：第一次所见即所得

最后，我的重心还是回到了 Codex CLI。

CLI 对新人当然不友好。

Command Line Interface。

光是这个 C、L、I，就足以吓跑一大群人。

但我很庆幸自己忍了下来。

第一次进入 Codex CLI 时，我需要理解的 slash 命令其实并不多。

最重要的大概是 /init。

它会要求 Codex 在项目根目录创建一个 AGENTS.md。此后，每次在这个目录启动 Session，这份文件中的内容都会被注入上下文。

剩下的无非是切换模型、调整思考强度、查看状态和退出。

当然，还有一个所有人点击次数最多的功能：

查看剩余额度。

Desktop 里是左下角头像。

CLI 里是 /status。

这个按钮，大概一直都是整个产品里使用频率最高的按钮。

Karpathy 曾经提到过一种“AI 精神病”：每天花大量时间和 AI 聊天，Token 用不完会焦虑。

但我想补充一句：

用完了也一样难受。

CLI 真正让我第一次感到安心，是因为它终于带来了某种所见即所得的体验。

我在输入框中写下需求。

它自己读取代码。

自己执行命令。

自己查看输出。

再根据输出修改。

模型、终端、文件系统和项目环境第一次真正处在了同一个闭环里。

但早期的交互仍然有明显的问题。

后台线程管理并不透明。

开发服务器启动后，可能一直占着端口。

如果你通过 Command + Q 强制退出，早期 Codex 甚至可能继续保留没有通过 /quit 正常终止的线程。

Agent 的基本交互虽然已经成型，但人仍然无法完整看见它到底留下了什么。

这个问题在 2025 年底逐渐被淡化。

一方面，是模型能力的提升。

GPT-5.1、5.2，尤其是之后衍生出的 Codex 模型，已经从大量 Agent 成功和失败轨迹中，逐渐内化了线程管理、命令执行和环境维护能力。

另一方面，是 harness 和交互设计的共同演进。

后台进程开始被直接暴露在界面上。

强制退出时会提示终止线程。

Prompt Engineering、Context Engineering 等理论也开始在开发者社区流行。

更重要的是，它们不再只是几篇文章里的抽象理论。

它们逐渐变成了真实的产品行为。

开发者的使用经验、社区讨论、GitHub 上关于 Plan 模式的 communication，以及产品经理对反馈的回应，共同塑造了这些后来让人感到安心的能力。

那是我最狂热的一段时间。

每一份 Release Note，我都会认真阅读。

生怕漏掉任何一个 CLI 版本里的新特性。

## 四、从不伦不类，到真正的入口

2026 年初，GPT-5.3 Codex 和 Codex Desktop 到来。

印象里，大约就在新年前后。

我第一时间下载了 Desktop。

但开发者最初的反馈并不算积极。

有人说它臃肿。

有人说它脱裤子放屁。

也有人觉得产品定位不清。

尤其是几个非常奇怪的点：

应用里可以通过 UI 完成 Git Commit 和 Push，却不能通过 UI 做 Git Pull。

可以查看当前改动的 Diff，却没有真正的文件树。

它像是卡在传统 IDE 和 CLI 之间。

但具体卡在两者之间的哪里，又很难说清楚。

我早期对它的评价是：

> 不伦不类。

所幸，产品持续推进，最终让 Codex Desktop 成为大部分开发者进入 Codex 的入口。

这是正确的选择。

我始终认为，TUI 是一种过渡形态，GUI 才是更自然的方向。

线程管理、模型切换、终端创建、任务切换，以及最重要的——查看剩余额度——都可以通过光标完成。

这才是对的。

随着产品公信力建立起来，我也理所当然地相信：Codex 团队应该最懂自己家的模型。

我长期使用 ChatGPT 的模型，自然也就没有太多理由切换到其他 Coding Agent。

但后来我逐渐意识到，真正的壁垒并不只在 UI。

甚至不只在模型。

它来自模型、harness、代码环境、工具系统、文档规范、线程组织和用户信任共同形成的整体。

代码是最好的上下文。

但只有代码，也并不够。

## 五、没有银弹：胶水代码、过度防护与 Goal

GPT-5.4 和 5.5 的时代，中文开发社区开始频繁讨论两个问题：

**胶水代码**和**过度防护**。

那时，已经出现了一部分完全不再 Review 代码的人。

有时 Vibe 了一大坨，功能也勉强能跑，但往下看就会发现，真正跑偏的并不是表层功能，而是底层设计。

一个最真实的场景是：

你让 Codex 根据需求画出一个令你满意的 Workflow。

然后告诉它：

“完整完成。”

很明显，它不会真的完整完成。

你继续追问，它会告诉你还有一部分。

再追问，它仍然会说还有一部分。

Goal 模式也随之出现。

可以把 Goal 粗略理解为一个持续状态机。

只要 Goal 仍然存在，任务就处于未完成状态。每完成一个 Turn，Agent 都要判断是否可以将 Goal 标记为完成。

如果没有完成，它会在下一个 Turn、下一次上下文压缩，或者其他 Hook 时机再次被注入。

于是社区里开始出现很多截图。

有人让 Goal 连续运行几个小时，甚至几天。

Goal 的确提供了一种追逐明确目标的方式。

但问题是，在 Agent Coding 已经发展了这么久、用户提示词越来越抽象简短的时候，又有多少人会认真定义 Goal 的退出条件？

如果退出条件不清晰，Goal 很容易进入循环。

我自己就遇到过一个真实案例：

Agent 需要调用一个 CLI 工具的 Token，才能搭建自动测试。

工具授权需要由我完成。

但“搭建自动测试”的 Goal 又没有完成。

于是 Agent 不会停下。

未完成状态持续触发 Next Turn。

它一次次重新尝试。

最终进入死循环。

因此，我至今仍然认为，Goal 最适合的场景，是功能层面的确定性操作，比如 E2E Test、批量验证、明确的数据迁移。

至于构建、开发和架构这一层，我并不敢完全相信它。

因为这里涉及的不只是“做完没有”，还涉及：

> 做成什么样才算对？

这也是胶水代码问题最难解决的地方。

Agent 很擅长局部合理性。

这个异常，可以再捕获一次。

这个参数，可以再兼容一种格式。

这里可以增加一个 fallback。

这个测试失败，可以再增加一个 mock。

为了避免一个边缘情况，可以再多做一层封装。

每一次修改，在局部看起来都很合理。

但当所有局部合理叠加起来，系统就可能失去整体上的概念完整性。

这正是《人月神话》中最重要的思想之一：

> 一个优秀的软件系统，需要统一的设计意志。

Agent 可以不断生成局部正确的代码，却并不会天然保护整个系统的一致性。

所以，人机协作中最困难的矛盾开始出现。

如果人对项目拥有很强的把关力度，就需要步步 Review、持续理解、不断确认。

这样一来，人会失去“放手一搏”的潇洒。

但如果放任 Agent 自由发挥，人的决策点和控制点又会快速减少。

说得好听，这是自动化。

悲观一点看，就是抽卡。

你可能放任 Agent 把一个并不重要的测试集膨胀到上千个，只因为你最开始对某个功能多做了一层防护。

你也可能得到一套所有测试都通过、却没有人真正理解的系统。

我到现在依然没有找到天衣无缝的解决方法。

整个 Agent Coding Workflow，从外部看，依然带有黑盒性质。

你可以在 AGENTS.md 里强调“不要过度防护”。

但一轮上下文压缩之后，这条规则还剩多少？

如果每个 Turn 都重新注入，又会不会干扰模型本身的判断？

人机合作的最高境界，也许是双方始终保持信息同步。

但究竟应该同步到什么程度，我仍然不清楚。

## 六、从人月神话，到 Token 神话

传统的软件管理者曾经相信：

> 十个人做十个月的工作，换成一百个人，一个月就能完成。

这就是人月神话。

而在 Agent 时代，我们正在产生一种新的幻觉：

> 多开几个 Agent，多给一些 Token，多运行几个小时，再加一个更长的上下文，就能得到更好的软件。

但实际经验并不是这样。

Token 更多，不代表方向正确。

上下文更长，不代表所有信息都会被正确使用。

思考时间更久，不代表判断会更加坚定。

Agent 更多，不代表系统会更加统一。

Goal 持续得更久，不代表距离完成更近。

测试数量更多，不代表软件质量更高。

自动化程度更高，也不代表人的心智压力更低。

Token 不是新时代的人月。

但我们正在用管理人月的方式管理 Token。

我们会计算额度。

计算并行任务数。

计算上下文窗口。

计算模型工作了几个小时。

然后把这些数字错误地等同于生产力。

可真正的软件产出，从来不是：

> Agent 数量 × Token 数量 × 运行时间。

它更接近：

> Agent 执行能力 × 需求清晰度 × 架构一致性 × 验证能力。

其中任何一项接近零，最终结果都可能接近零。

这也是为什么 AI 并没有成为软件工程的银弹。

它确实在快速消灭大量偶然复杂性：

语法、模板代码、环境命令、重复劳动、接口调用、测试生成、浏览器操作。

但软件中的本质复杂性仍然存在：

需求是什么？

边界在哪里？

哪些功能真正重要？

系统应该如何抽象？

什么时候应该停止？

谁来承担最终责任？

当编码成本逐渐趋近于零时，需求理解、架构判断和结果验证，反而会成为更加昂贵的部分。

代码开始变得廉价。

判断开始变得昂贵。

## 七、5.6：信息过载，与人的决策带宽

和 GPT-5.6 Sol 对话时，这种变化尤其明显。

当你要求它给出一个推荐方案时，它默认会输出大量信息。

主观判断和客观事实混合在一起。

你需要接受它的观点，反驳它的观点，提取其中的客观信息，再和它辩驳。

它会更新方案。

它不够坚定。

它会顺从。

它也可能在更新过程中遗漏先前的信息。

这一切会给人带来很大的心智压力。

人和 Agent，都需要保持头脑清醒，才能做出决定。

我目前的应对方法只有两个。

第一个，是限制输出。

我会明确要求：

> 只输出关键信息，并指出需要我决定的决策点。

这句话的重点，并不只是让模型少说一点。

真正重要的是“决策点”。

我不需要 Agent 向我直播全部过程。

我需要它告诉我：

- 哪些是已确认事实；
- 哪些是它的判断；
- 哪些选择会改变系统方向；
- 哪些事情需要由我承担决定。

第二个方法，是持续维护外部文档。

现在 Codex 已经可以直接渲染 Mermaid 流程图。

对着 Workflow 做决定，会比对着几千字的自然语言清醒很多。

AGENTS.md、设计文档、接口约束、Mermaid、决策记录，本质上都像是 Agent 时代的“项目手册”。

它们的目的不是控制 Agent 的每一个动作，而是维持系统的概念完整性。

有时，我会花二三十分钟去思考一个尽可能完整的提示词，覆盖我能想到的方向、边界和限制，再让 Agent 去执行。

表面上看，这好像降低了效率。

我花了二十三分钟写提示词，模型才开始干活。

但换个角度看，这二十三分钟并不是在“研究如何讨好模型”。

而是在完成需求分析、约束设计和验收标准。

我思考完，轮到它思考。

随后，我终于可以喘息片刻。

## 八、Side Talk：不是删除对话，而是降低提问成本

如果你也是 Codex 的早期用户，也许会和我一样困惑：

为什么他们长期不提供明显的 Session Delete，却一直力推 Archive？

很多对话只是一个很简单的问题。

以后肯定不会再用。

我为什么只能归档，不能直接删除？

过去我一直觉得这很别扭。

后来只好安慰自己：

反正那么多对话都保存在 .codex/session 里，再攒一些，说不定以后可以美美地把自己蒸馏成 Skill。

最近出现的 Feature，才真正回答了这个问题：

**Side Talk 和 Task Tool。**

删除功能也终于到来。

但奇怪的是，等它真的出现，我已经不会特意去找它了。

Side Talk 可以从当前聊天节点直接 Fork 出一个临时独立对话。

它和过去的 Fork 不同。

过去的 Fork 颗粒度更接近 Turn，适合在完成同一轮信息探索后，分叉开发不同功能。

Side Talk 的颗粒度则更接近瞬间。

Agent 正在运行一个命令。

你觉得不太对劲。

可以立刻 Side Talk：

“你为什么要执行这个命令？”

它类似 Claude Code 的 /btw。

这个功能看起来很小，但它极大增强了人对事实的掌控。

而且对话是临时的。

不会出现在侧边 Session 选择器里。

不会污染 Main Task 的上下文。

最新版本中，主任务和侧边对话的思考强度也可以独立调整。

于是，人终于有勇气随时提问。

随时怀疑。

随时尝试。

又不必担心自己的发散污染主任务。

侧边探索得到的信息，还可以通过 Send Message Tool，总结为客观事实传回 Main Task。

Main Task 再根据这些信息继续完成工作。

到这个时候，我才理解：

Archive 并不是单纯在回避删除。

产品真正试图解决的，是如何让一次长期工作的上下文持续生长，同时又允许人进行临时探索。

删除减少的是存储。

Side Talk 减少的，是提问的心理成本。

最后，我也逐渐忘掉了 Delete。

现在即使在网页版 ChatGPT，我也更愿意 Archive，而不是 Delete。

它确实减少了很多心理负担。

## 九、Remote Control：Cloud 最初的愿景终于闭环

和 Side Talk 一起到来的，还有 Remote Control。

它与 Work 模式、原本的 Cloud 模式一起，最终形成了一个闭环。

以前如果有人问我：

“你最推荐小龙虾这类 Agent 的地方是什么？”

我可能会思考片刻，然后回答：

它可以持久化部署。

你可以通过微信之类的工具给它发消息，让它操作你的电脑。

我经常举的例子是：

你有一个文件放在电脑里。

出门以后突然要用。

于是给 Agent 发一条消息，它就把文件找出来发给你。

这是我过去对龙虾类 Agent 的理解。

但 Remote Control 出现之后，所有设备可以直接被串联起来。

公司的电脑。

远在美国的 Linux 服务器。

不知道被扔在哪个角落的 Mac mini。

以及你手中的手机。

它们通过 Codex 网络直接连通。

你可以在手机上向每一台设备发送任务。

我的一个小 Tip 是，现在 Shadowrocket 已经直接内置了 Tailscale。

再加上内网穿透，所有设备都可以通过 Remote Control 和 Tailscale 连在一起，并通过 MagicDNS 直接 SSH。

你可以在本地开发。

可以挂容器。

可以和 partner 共用一台预发布环境机器。

也可以给购买的 VM 安装 Codex，需要配置服务时，直接从手上的另一台设备发送消息。

甚至不再需要开放公网 SSH。

回看 Codex 的发展路线，它从一开始就在同时推进两件事：

一条路线，是面向人类的交互。

另一条路线，是让能力本身 CLI 化、工具化。

即使一个能力没有直接暴露给人，也会尽可能通过命令、工具或接口暴露给 Agent。

这一点，最终构成了 Remote Control 的基础。

再回到最早那个看起来笨重、反馈极差的 Cloud，也许直到今天，我们才真正看清它一年前的愿景。

Cloud 从来不只是让代码在远端跑起来。

它真正想做的，是让工作脱离具体设备，成为一个可以随时接续的任务对象。

## 十、Computer Use：跨越人与机器的最后一层界面

Codex Desktop 的另一个壁垒，是 Computer Use。

配合经过路径训练的 GPT-5.6，它展现出了非常惊人的自动化能力。

Computer Use 与内置侧边浏览器形成闭环。

它可以复用 CDP 登录态，直接打通企业工作平台。

再配合网页批注功能，用户可以对页面组件指哪打哪。

现在，我不少前端设计的 E2E 验证，已经很少再专门编写 Playwright 脚本。

Agent 可以直接打开页面、点击组件、填写内容、观察结果。

它甚至开始打通移动端和客户端开发的自动化调试。

尤其是小程序。

在 Suanxian 项目里，这种能力带来的变化非常明显。

很有意思的是，跨越人与机器界面的能力，最后居然借助的是无障碍模式。

过去，无障碍接口是为了让更多人能够操作计算机。

现在，它又开始帮助机器理解和操作人类界面。

## 十一、Ultra：Agent 时代的外科手术式团队

不久之前，GPT-5.6 一起带来了 Ultra Reasoning Effort。

从现有表现来看，Ultra 的实际思考强度接近 Max，同时加入了一套子代理策略。

官方目前并没有完整公开这一策略的细节。

我也发现了一个有些矛盾的地方：

在 API 模式中，子代理似乎可以作为一个独立开关存在。

也就是说，从表面上看：

> Ultra ≈ Max Reasoning + 子代理策略。

那为什么低思考强度不能独立开放子代理策略？

随着官方收回 372K 上下文，这个问题变得更加明显。

上下文缩小意味着更频繁的压缩，也意味着更强的信息丢失焦虑。

但实际使用下来，Codex 的上下文压缩确实带有某种黑魔法。

它的压缩效率很高。

在和 GPT-5.6 实战的这两周里，我获得了很强的安全感。

我仿佛可以在同一个对话中，一直处理同一份长期工作。

项目密钥、不同机器的连接方式、服务 Key、环境配置、历史决策，都可以在一个持续工作的上下文中被反复使用。

尤其是 Ultra 模式。

刚开始使用时，我觉得它有些机械、生硬。

但在超长对话中，它展现出的清醒程度让我震惊。

这种感觉很像我第一次在 Claude Code 中使用 Opus，让它调用两个 Sonnet 子代理去收集信息。

相似的地方，不只是它们都使用了子代理。

而是主 Agent 在关键判断节点，对信息拥有更强的把控。

在泄漏出来的 Claude Code 工具提示词里，我曾特意查看过这一点：

面对横向、广范围的信息探索，应当 Spawn 子代理。

Ultra 的具体策略我们仍然不得而知。

但从实际体验来看，它在跨仓库、跨服务、跨机器的工作中，确实展现出了近乎奇迹般的清醒。

在一个同时涉及两个仓库、两台开发机、一个数据库，以及三四个外部文档链接的任务里，即使上下文已经缩紧到 272K，它仍然能够做出非常犀利的判断。

这让我想到《人月神话》中的“外科手术式团队”。

一个核心设计者负责整体判断。

其他成员承担资料收集、测试、工具和局部实现。

真正重要的不是团队人数，而是整个系统是否保持统一意志。

Ultra 的价值，也许不只是“调用了更多 Agent”。

而是它开始形成一种组织结构：

主 Agent 保持核心目标。

子代理负责横向探索。

工具负责传递事实。

最后，决策重新回流到一个中心。

但需要注意的是，即使如此，长期项目中真正稳定存在的“首席设计者”，目前仍然不是某一次 Session 里的主 Agent。

而是人，以及人持续维护的外部文档、系统边界和历史决策。

Agent 可以成为首席程序员。

但人仍然是那个决定“我们究竟要建造什么”的人。

## 十二、Token 焦虑，和 Tibo 大恩人

当然，Ultra 消耗 Token 的速度也非常快。

Tibo 是大恩人。

他会一直 Reset。

但不断 Reset，也解决不了人们频繁点击查看剩余额度的问题。

他们是真的有算力。

我个人认为，取消五小时 Limit 是正确的。

大家都是成年人了，自己学会管理额度就好。

但持续的 Reset，确实会给人一种很奇妙的感觉：

仿佛官方在说：

“快来，继续帮我压测。”

Altman：

“Tibo，做以下压测。”

Tibo：

“Reset。”

## 十三、服务 CLI 化，以及 Agent 作为入口

还有一个不能忽略、甚至可以说正在造福世界的趋势：

外部服务正在 CLI 化。

上到飞书。

下到瑞幸。

没错，甚至有点咖啡 CLI。

非常抽象。

但 CLI 是 Agent 的来处。

当外部服务开始 CLI 化，它们就像一块块意义非凡的拼图，被接入 Agent 生态。

这进一步增强了 Agent 作为统一入口的趋势。

你在 Codex 一个应用里可以做的事情越来越多。

再加上 Work 与 Chat 的整合，现在通过网页版 ChatGPT，甚至调用 Pro 系列模型完成的调研，也可以直接 Add to Codex Task。

Codex 正在向超级应用推进。

MCP、Skill、CLI 和各种外部能力，一块块拼图共同构成了现有的交互形态。

我已经逐渐沉浸其中，几乎感受不到突兀。

剩下需要思考的问题，也许反而是人的输入。

在安静的办公室里，如何实现更高效的语音输入？

或者，如何拥有更快的打字速度？

我不希望自己的输入速度成为人机交互中的瓶颈。

但我真的无法接受，在安静的办公室里对着电脑大声讲话。

## 十四、真正昂贵的，是判断

大概就是这样了。

文章写于 7 月 23 日。

在这个时间点，Agent 已经开始通过代码真实地改变世界。

模型 Reasoning 出命令。

命令运行在个人终端。

一块块工具和服务拼图彼此打通。

我已经在这里体验了一年，也烧掉了超过 20B 的 Token。

它逐渐成为我连接计算机和世界的入口。

但这一年最终让我明白的，并不是“AI 可以替我写多少代码”。

而是：

> 当代码生产能力接近无限时，我们应该如何管理它？

AI 没有推翻《人月神话》。

它只是把《人月神话》从人与人的协作问题，迁移成了人与 Agent、Agent 与 Agent、上下文与系统之间的协作问题。

过去稀缺的资源，是程序员的编码时间。

现在代码供给逐渐变得充裕。

新的稀缺资源是：

人的注意力。

对业务的理解。

架构判断。

上下文一致性。

验证带宽。

以及对最终结果负责的能力。

Agent 带来的不是软件工程的消失。

恰恰相反。

它迫使软件工程剥离掉“写代码”这一层表象，重新显露出自己的本质：

定义问题。

设计系统。

维持完整性。

验证结果。

做出决定。

代码正在变得越来越廉价。

但判断正在变得越来越昂贵。

我还有更远的计划。

下一份实习。

下一个项目。

再远一些，也许是下一个国家。

毫无疑问，它也会继续陪着我。

去到未来人生中的更多地方。
